# M0 运行与学习指南：从进入环境到退出

当前开发板已经安装好环境和模型，项目统一位于 `/root/mini-llm-ascend`。日常使用直接从第 1 步开始，**不需要重复创建环境或安装依赖**。

以下 Bash 命令都在**开发板的 SSH 终端**中执行。当前 M0 通过命令行运行环境探测、测试和单请求推理；推理命令执行完会回到终端，API 服务尚未实现。

操作顺序：**进入项目并激活环境 → 检查环境 → 执行测试 → 启动推理 → 查看结果 → 退出环境**。

## 1. 进入项目和 Python 环境

每次新开 SSH 终端，完整执行这三条命令：

```bash
cd /root/mini-llm-ascend
source /usr/local/Ascend/ascend-toolkit/set_env.sh
source .venv/bin/activate
```

| 命令 | 作用 |
| --- | --- |
| `cd /root/mini-llm-ascend` | 进入项目根目录，下面的相对路径都以这里为起点 |
| `source /usr/local/Ascend/ascend-toolkit/set_env.sh` | 为当前终端加载昇腾 CANN 的运行环境 |
| `source .venv/bin/activate` | 激活项目内的 Python 环境，让 `python` 和 `pip` 指向 `.venv` |

激活成功后，终端提示符通常带有 `(mini-llm-ascend)`。再执行下面两条命令确认，不要只看提示符：

```bash
pwd
command -v python
```

预期依次输出：

```text
/root/mini-llm-ascend
/root/mini-llm-ascend/.venv/bin/python
```

**后续所有命令都假定你已完成本节，且仍在项目根目录。** 新开终端或重新连接 SSH 后，需要再次执行进入环境的三条命令。

## 2. 检查 NPU 环境是否正常

执行环境探测：

```bash
python -m bench.probe_env --device npu --output results/environment-npu.json
echo "退出码：$?"
```

脚本会记录 Python、依赖库、CANN、设备信息，并检查 matmul、index_select、softmax 和 argmax 是否能在 NPU 上得到正确的小张量结果。

成功时会看到类似输出：

```text
正在检查 matmul（首次调用可能编译算子）……
正在检查 index_select（首次调用可能编译算子）……
正在检查 softmax（首次调用可能编译算子）……
正在检查 argmax（首次调用可能编译算子）……
报告已保存：results/environment-npu.json
探测通过
退出码：0
```

如果显示“探测失败”或退出码非 0，先查看报告，不要继续把模型运行结果当成有效基线：

```bash
python -m json.tool results/environment-npu.json
```

重点看 `error` 和 `smoke_tests` 中哪些项目的 `ok` 为 `false`。`npu-smi` 的 Health 字段也会保存到报告；算子探测通过不代表所有设备健康告警已排除。

## 3. 如何执行代码测试

在相同的项目目录和环境中运行：

```bash
python -m unittest discover -s tests -v
echo "退出码：$?"
```

当前版本有 **7 项测试**。成功输出的末尾类似：

```text
Ran 7 tests in ...s

OK
退出码：0
```

这里的 `...s` 代表实际耗时，每次可能不同。测试覆盖计时边界、提前 EOS、固定输出长度、中断保存报告，以及随机小 Qwen3 与 HF 直接生成的对照。测试不需要下载模型，其中小模型集成测试运行在开发板 CPU 上。

看到 `FAILED`、`ERROR` 或非 0 退出码时，保存错误信息并排查；出现一条 `Warning` 本身不等于测试失败，最终还要看测试结果。

第 2 步验证基础 NPU 算子，第 3 步验证代码行为；下面的第 4 步才会加载真实 Qwen3-0.6B 权重。

## 4. 启动 Qwen3 推理

### 4.1 首先跑一次最短验证

```bash
python -m bench.baseline \
  --model ./models/Qwen3-0.6B \
  --device npu \
  --max-new-tokens 1 \
  --warmup 0 \
  --runs 1 \
  --output results/qwen3-smoke.json
echo "退出码：$?"
```

可以整段复制执行。多行末尾的 `\` 表示命令尚未结束，**不要在反斜杠后面添加空格**。

程序会依次保存诊断报告、加载模型、运行生成、显示生成文本并返回终端。因为只生成 1 个 token，文本可能很短，甚至没有可见文字；不要把它当成完整回答。成功应同时满足：

- 终端退出码为 `0`。
- 报告中的 `status` 为 `ok`，`stage` 为 `complete`。
- 报告记录了实际生成的 token。只有 1 个 token 时，`tpot_ms` 为 `null` 是正常的。

查看状态：

```bash
python -c "import json; r=json.load(open('results/qwen3-smoke.json')); print('状态:', r['status']); print('阶段:', r.get('stage')); print('错误:', r.get('error'))"
```

### 4.2 再跑可比较的短请求基线

最短验证通过后，执行以下命令：

```bash
python -m bench.baseline \
  --model ./models/Qwen3-0.6B \
  --device npu \
  --max-new-tokens 8 \
  --fixed-length \
  --warmup 1 \
  --runs 3 \
  --output results/qwen3-npu.json
echo "退出码：$?"
```

| 参数 | 含义 |
| --- | --- |
| `--model ./models/Qwen3-0.6B` | 从项目内加载本地模型，不自动下载 |
| `--device npu` | 使用 NPU；初始化失败会报错，不会自动改跑 CPU |
| `--max-new-tokens 8` | 本次最多生成 8 个新 token |
| `--fixed-length` | 抑制提前 EOS，统一输出长度，用于性能实验 |
| `--warmup 1` | 先运行 1 轮预热，该轮不计入性能汇总 |
| `--runs 3` | 预热后测量 3 轮 |
| `--output ...` | 保存 JSON 报告；同名文件会被覆盖，需要保留多次结果时请换文件名 |

成功时会看到“样本 1”“样本 2”“样本 3”、各轮速度与生成文本，最终退出码为 0。

想换问题，可在命令中添加：

```text
--prompt "请用一句话解释什么是大模型推理。"
```

8 token 可能不足以形成完整回答。后续可将 `--max-new-tokens 8` 改为 `32`，同时把输出文件改为 `results/qwen3-npu-32.json`；新长度可能触发额外编译。已归档的初测仅覆盖 21-token 输入、8-token 输出，不代表已验证 32-token 性能。

### 4.3 第一次运行慢时怎么办

首次模型加载和算子编译可能耗时数分钟甚至更久。此前首次成功的 8-token 生成曾耗时约 17 分钟，预热后同类短请求才明显变快。不要把首次编译耗时直接当成稳定推理速度。

如果需要查看进度，可以**另开一个 SSH 终端**，先执行第 1 步，再读取当前报告：

```bash
python -c "import json; r=json.load(open('results/qwen3-npu.json')); print('状态:', r['status']); print('阶段:', r.get('stage')); print('已完成样本数:', len(r.get('runs', [])))"
```

运行最短验证时，将文件名换为 `results/qwen3-smoke.json`。

| 报告状态/阶段 | 含义 |
| --- | --- |
| `status: running` | 本次命令还未完成 |
| `stage: loading_model` | 正在加载模型或将模型搬到设备 |
| `stage: warmup` | 正在预热 |
| `stage: measuring_run_1` 等 | 正在测量对应样本 |
| `status: ok`、`stage: complete` | 本次基线已完成 |
| `status: error` | 失败，查看 `error` 字段 |
| `status: interrupted` | 收到中断，不能当成完整基线 |

报告在阶段变化和每轮结束时写入，不是实时进度条。恰好在写入时读取可能遇到 JSON 解析错误，稍后重读即可；异常终止后残留的 `running` 也不能单独证明进程仍在运行。

## 5. 查看结果和理解指标

基线结束后，打印状态和汇总：

```bash
python -c "import json; r=json.load(open('results/qwen3-npu.json')); print('状态:', r['status']); print(json.dumps(r.get('summary', {}), ensure_ascii=False, indent=2))"
```

需要查看每轮的输出文本、token IDs、参数和环境信息时：

```bash
python -m json.tool results/qwen3-npu.json
```

| 指标 | 含义 |
| --- | --- |
| `load_s` | 模型加载和搬到设备的时间，单独统计 |
| `ttft_ms` | 输入已准备好后，从开始生成到主机收到第一个 token 的时间 |
| `tpot_ms` | 首 token 之后，相邻 token 时间间隔的平均值；单 token 输出为 `null` |
| `generate_s` | 整次生成调用耗时，含结束整理和设备同步 |
| `output_tokens_per_s` | 实际输出 token 数 / 生成调用耗时 |
| `finalization_ms` | 最后一个 token 之后的结束整理时间 |

这些是单请求生成链路的主机观测指标，包含 HF 框架与相关数据搬运，不包含服务端排队和网络耗时。NPU 内存字段来自框架分配器，不代表整块开发板的总内存占用。3 个短样本不能推出稳定 P99。

已完成的原始数据和限制见[310B4 实验记录](experiments/m0-310b4/README.md)。日志中的 CPU fallback、`storage_offset` / `result is untrustworthy` 警告需要保留，完整模型精度仍需在 M1 做逐层对拍；生成成功不等于完整精度验证通过。

## 6. 中断程序、退出环境和退出 SSH

### 程序还在运行，想停止

在**运行该命令的终端**按 `Ctrl+C`，等待程序返回命令提示符。基线会尝试保存 `interrupted` 报告；原生算子调用可能要等返回 Python 后才能响应。此时不要继续向正在运行的程序输入 `deactivate`。

### 程序已结束，只退出 Python 环境

```bash
deactivate
```

执行后，提示符里的 `(mini-llm-ascend)` 通常消失，`python` 恢复为激活前终端使用的解释器。你仍在开发板上，也仍在当前目录；项目文件、模型和依赖不会被删除。`deactivate` 只撤销虚拟环境激活，不负责清除先前加载的 CANN 环境变量。

在同一个终端重新进入环境：

```bash
cd /root/mini-llm-ascend
source .venv/bin/activate
```

如果是新终端或重新连接 SSH，重新执行第 1 步的完整三条命令。

### 退出开发板 SSH 会话

先确认前台程序已结束，再执行：

```bash
deactivate
exit
```

如果刚才已经执行过 `deactivate`，直接输入 `exit` 即可。不要依赖关闭 SSH 窗口让前台推理可靠地在后台继续。

## 7. 代码学习顺序

配套的[M0 代码设计与原理](M0代码设计与原理.md)逐个解释函数职责、调用流程、张量形状、TTFT/TPOT 计算和测试设计，建议与源文件对照阅读。

1. `bench/common.py`：环境信息、设备选择、同步和 JSON 保存。
2. `bench/probe_env.py`：小张量 NPU 结果与 CPU FP32 参考对比。
3. `bench/baseline.py`：模型加载、prompt 编码、预热、生成计时与汇总。
4. `tests/test_baseline.py`：为什么 prompt 不算输出 token、EOS 提前结束如何计数、单 token 为什么没有 TPOT。

当前使用 HF 的 Qwen3 实现，后续 M1 才手写前向。代码默认关闭 thinking，使用 greedy 便于对拍，并设置 `use_model_defaults=False`，避免模型默认采样参数覆盖实验设置。greedy 是实验选择，不是 Qwen 推荐的回答质量采样设置。[Qwen 官方说明](https://huggingface.co/Qwen/Qwen3-0.6B)

CPU 模式默认 FP32，NPU 模式默认 FP16。需要 CPU 诊断时，可将 `--device npu` 改为 `--device cpu`；CPU 结果不能当成 NPU 性能基线。

## 8. 首次安装（当前开发板可以跳过）

仅在新开发板尚未创建项目环境时执行。先确保项目源码已在指定目录，且板载 Python、torch、torch_npu 和 CANN 可用：

```bash
cd /root/mini-llm-ascend
source /usr/local/Ascend/ascend-toolkit/set_env.sh
/usr/local/miniconda3/bin/python -m venv --system-site-packages --prompt mini-llm-ascend .venv
source .venv/bin/activate
python -m pip install --only-binary=:all: -r requirements-m0.txt
```

模型目录 `models/Qwen3-0.6B` 需要包含配置、tokenizer 和完整 safetensors 权重，权重不进入 Git。依赖文件固定了关键模型加载依赖，但不是全量锁文件；探测报告会记录实际版本。无外网时需要准备对应 Python 3.9 / aarch64 的安装包，不能使用 Windows wheel。

不要直接升级板载 torch、torch_npu 或 CANN。当前项目依赖这套配套环境；环境与模型目录说明见[目录与部署](目录与部署.md)。

## 9. 常见问题

| 现象 | 先检查什么 |
| --- | --- |
| `source .venv/bin/activate` 报文件不存在 | `pwd` 是否为 `/root/mini-llm-ascend`；当前开发板的环境已准备好，不要在别的目录重复创建 |
| `python` 仍指向系统 Python | 重新执行激活命令，再运行 `command -v python` |
| `No module named bench` | 是否在项目根目录执行 `python -m ...` |
| 找不到 torch_npu 或 NPU 初始化失败 | 是否加载了 CANN 环境，是否使用项目 Python；先运行环境探测 |
| `KeyError: qwen3` | 核对 Transformers 版本，本项目固定为 4.51.3 |
| 找不到模型配置或权重 | 确认 `--model` 指向项目内 `models/Qwen3-0.6B` |
| 测试出现 `FAILED` / `ERROR` | 保存完整错误，先处理后再继续测性能 |
| Windows Anaconda 报重复 OpenMP 库错误 | 当前指南在开发板执行；本机需另行准备兼容环境，不用允许重复库的开关掩盖问题 |

本阶段不使用配置草案中的 8 GiB 引擎 KV 池，HF 按单次请求管理缓存。报告会记录本地模型清单和配置哈希；`--model-revision` 只用于填写已知来源，不会自动认证权重身份。正式对比时应另行核对权重校验和。
