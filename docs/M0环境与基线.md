# M0：环境探测与 Qwen3 单请求基线

本阶段先回答两个问题：这套软件能否在目标设备上正确执行？未经自研优化的单请求推理有多快？这里调用 Hugging Face 模型，后续 M1 才手写前向。

已完成的 8-token 板端初测及原始报告见[实验记录](experiments/m0-310b4/README.md)。下面的 32-token 命令用于后续扩展，不代表已完成该长度的测量。

## 1. 阅读顺序

1. `bench/common.py`：版本记录、CPU/NPU 选择、同步和报告保存。
2. `bench/probe_env.py`：小张量操作与 CPU FP32 参考对拍。
3. `bench/baseline.py`：模型加载、prompt 编码、预热、生成计时与汇总。
4. `tests/test_baseline.py`：为什么 prompt 不算输出、提前 EOS 怎么计数、单 token 为什么没有 TPOT。

只支持单请求、batch=1。默认 NPU 使用 FP16，CPU 使用 FP32；设备必须明确指定，不做自动回退。所有模型文件从本地读取，不下载代码或权重。

## 2. 开发板准备

先进入仓库根目录，使用板载 Python 创建隔离环境，复用已有 torch / torch_npu。以下命令假定 CANN 和 Python 位于原设计记录的位置，其他机器需要调整路径。

```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh
/usr/local/miniconda3/bin/python -m venv --system-site-packages /root/mini-llm-m0-venv
/root/mini-llm-m0-venv/bin/python -m pip install --only-binary=:all: -r requirements-m0.txt
```

依赖文件固定 Transformers 及关键模型加载依赖，但不是全量锁文件；环境报告记录实际解析出的版本。固定 hub 0.30.2 可避免较新 hf-xet 在旧 aarch64 环境触发源码构建。不要执行会升级板载 torch、torch_npu 或 CANN 的安装命令。无外网时可在其他机器准备对应 Python 3.9/aarch64 的 wheel，再传输安装；不能把 Windows wheel 用到开发板。

模型目录至少包含 `config.json`、`generation_config.json`、tokenizer 文件与完整 safetensors 权重。示例路径为 `/root/models/Qwen3-0.6B`，权重不入库。

## 3. 先探测环境

```bash
/root/mini-llm-m0-venv/bin/python -m bench.probe_env \
  --device npu --output results/environment-npu.json
```

探测内容：Python/库版本、Git 状态、CANN 信息、`npu-smi`、系统内存，以及 matmul、index_select、softmax、argmax 的正确性。退出码非零意味着目标设备或基础算子未通过，不能据此宣称模型可运行。

小算子计时仅用于诊断，不是芯片峰值算力或有效带宽测量。CPU 模式下没有 `npu-smi` 是正常现象；报告会记录缺失，不阻止 CPU 测试。

## 4. 跑单请求基线

第一次先用短输出验证链路：

```bash
/root/mini-llm-m0-venv/bin/python -m bench.baseline \
  --model /root/models/Qwen3-0.6B --device npu \
  --max-new-tokens 1 --warmup 0 --runs 1 \
  --output results/qwen3-smoke.json
```

通过后再预热并记录固定长度的 3 个样本：

```bash
/root/mini-llm-m0-venv/bin/python -m bench.baseline \
  --model /root/models/Qwen3-0.6B --device npu \
  --max-new-tokens 32 --fixed-length --warmup 1 --runs 3 \
  --output results/qwen3-npu.json
```

首次算子编译可能耗时数分钟甚至更久。报告会提前记录 `loading_model`、`warmup`、`measuring_run_*` 阶段；可用 Ctrl+C 中断并保存 `interrupted` 状态。部分样本不能当成完整基线。编译中的原生调用可能要到返回 Python 后才能响应中断。

默认关闭 thinking，用 greedy 保证易于对拍。它是实验设置，不是 Qwen 推荐的质量采样参数。`--fixed-length` 会抑制提前 EOS，适合统一负载，不代表真实对话质量；不用该开关时按真实输出长度计数。[Qwen 官方说明](https://huggingface.co/Qwen/Qwen3-0.6B)

代码显式传入 `use_model_defaults=False`：Transformers 4.51.3 否则可能将模型默认的采样设置补回生成配置，导致看似设了 greedy、实际上却在采样。测试使用带采样默认值的小模型验证这一点。

在本机 CPU 验证时，使用已安装 torch 与依赖的 Python，将 `--device npu` 换为 `--device cpu`，模型路径改成本机路径。CPU 结果只用于正确性检查，不与 NPU 性能直接排名。

## 5. 指标怎么读

输入先分词并搬到设备，然后同步设备，开始计时。HF `generate` 的首次 streamer 回调是 prompt，必须跳过；后续回调是已经搬到 CPU 的新 token。

| 字段 | 含义 |
| --- | --- |
| `load_s` | tokenizer/模型加载并搬到目标设备的时间，单独报告 |
| `ttft_ms` | generate 开始到 host 观察到第一个输出 token；包含 prefill 和生成框架开销 |
| `itl_ms` | host 观察到相邻 token 的时间间隔 |
| `tpot_ms` | ITL 平均值，即 `(最后 token 时间 - 首 token 时间)/(N-1)`；N=1 时为 null |
| `generate_s` | generate 开始到结束并完成设备同步，含结束整理开销 |
| `output_tokens_per_s` | 实际输出 token 数 / generate_s |
| `finalization_ms` | 最后 token 被观察到之后的结束整理时间 |

这些是**单请求生成链路的 host 观测指标**，不是服务端排队/网络 TTFT，也不是纯 kernel 耗时。每 token 的 CPU 搬运与 streamer 本身可能影响时延；后续对照组需保持相同口径。

报告保存每轮输出 IDs、文本、输入 IDs、完整生成参数、Git 状态和模型文件清单。默认不遍历哈希大型权重；`--model-revision` 用于填入已知来源 revision，不会自动验证来源。正式对比应另行校验权重，不能只凭文件大小判同一模型。

NPU 内存字段来自框架分配器，不能代表整块开发板的系统内存占用。只有 3 个样本时只报告 mean/median，不声称已测出稳定 P99。

## 6. 本机测试与常见问题

```bash
python -m unittest discover -s tests -v
python -m bench.probe_env --device cpu --output results/environment-cpu.json
```

测试用随机初始化的极小 Qwen3，不需要下载权重，验证 streamer 不改变贪心输出、固定输出长度、提前 EOS 和计时边界。

- 找不到 torch_npu：确认使用板端隔离环境、继承了板载 site-packages，并加载 CANN 环境变量。
- `KeyError: qwen3`：核对实际 Python 和 Transformers 版本。
- 模型加载或 NPU 算子失败：查看报告中的 `error`，保留环境与原始日志，不把 CPU 回退当成板端成功。
- 模型太慢：先用短输出验证，首次编译和运行不计入稳定性能样本。
- NPU 日志出现 CPU fallback：保留原始日志，实际测到的是混合执行链路，不宣称全算子运行于 NPU。
- NPU 日志出现 `storage_offset` / `result is untrustworthy`：生成成功不足以证明完整数值正确，保留警告并在 M1 逐层对拍前将性能结果标为初步数据。
- Windows Anaconda 出现重复 OpenMP 库错误：这是本机运行环境冲突，应使用兼容的独立 Python/PyTorch 环境；不要用允许重复库的开关掩盖问题来发布性能数据。本次功能集成测试在开发板 CPU 上执行。

本阶段不需要配置引擎 YAML 中的 8 GiB KV 池；HF 按本次请求动态管理缓存，避免把后续引擎规划参数误用到基线。
