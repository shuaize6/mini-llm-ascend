# M1 运行与学习指南

M1 实现了单请求 Qwen3 手写前向、连续 KV Cache、greedy 生成和 HF 对拍。下面的命令都在开发板 SSH 终端运行，项目目录统一为 `/root/mini-llm-ascend`。原理与函数说明见 [M1 代码设计与原理](M1代码设计与原理.md)。

## 1. 每次打开终端，先进入环境

```bash
cd /root/mini-llm-ascend
source /usr/local/Ascend/ascend-toolkit/set_env.sh
source .venv/bin/activate
```

三个命令分别负责：进入项目目录、加载 CANN 的库路径、选择项目 Python 环境。激活 Python 环境不能代替加载 CANN；即使测试选择 CPU，HF 在板上导入 NPU 适配模块时也可能需要 CANN 的动态库。

检查当前位置和解释器：

```bash
pwd
command -v python
```

应分别看到 `/root/mini-llm-ascend` 和 `/root/mini-llm-ascend/.venv/bin/python`。M1 沿用 `requirements-m0.txt`，已有 M0 环境无需重新安装或升级 torch/CANN。

板端验证时使用较小的编译并行度，减少首次编译的进程与内存压力：

```bash
export MAX_COMPILE_CORE_NUMBER=2
export TE_PARALLEL_COMPILER=2
```

这两个设置由当前板载 CANN 的 Python 编译组件读取，并记录在报告的 `environment.compiler_environment` 中。它们只作用于本 shell 后续启动的进程，不是模型数学或精度开关。板端完整模型检查应串行执行，不要同时启动另一份 NPU 探针或模型。

## 2. 先跑不依赖大权重的测试

```bash
python -m unittest discover -s tests -v
echo $?
```

M1 阶段共 27 项测试（含 M0 的 7 项），M2 新增 7 项，M3 新增 6 项；全量命令会包含后续阶段，数量随版本增加。成功时末尾应为 `OK`，紧接着的退出码为 `0`。M2/M3 各自只运行新增定向测试，不要求重复运行此全量命令。不能只看前面某一行 `ok`，也不能只看退出码而忽略导入异常。

测试使用 CPU 小张量、随机小模型和临时 safetensors 文件，不下载模型，也不能代替 NPU 验证。主要检查数学组件、权重严格加载、缓存越界/重置、异常隔离、EOS、HF 对拍及报告失败状态。

在加载大模型前，还可单独检查 NPU RoPE：

```bash
python -m bench.probe_m1_rope --device npu --output results/m1-rope.json
echo $?
```

它只使用小张量，无需权重。成功要求 `current_cos/current_sin` 与 HF 完全一致；报告中的 `legacy_device_frequency_outer` 是旧写法的诊断对照，不参与当前实现的通过判定。必须等探针结束后再启动完整模型。

## 3. 启动自研模型，生成一小段文字

先确认本地权重存在：

```bash
ls models/Qwen3-0.6B/config.json models/Qwen3-0.6B/model.safetensors
```

首次使用先输出一个 token，验证加载与 prefill：

```bash
python -m bench.m1 \
  --model ./models/Qwen3-0.6B \
  --device npu \
  --max-new-tokens 1 \
  --output results/m1-smoke.json
echo $?
```

再运行 8-token 固定长度生成，覆盖 decode：

```bash
python -m bench.m1 \
  --model ./models/Qwen3-0.6B \
  --device npu \
  --prompt '请用一句话解释什么是KV缓存。' \
  --max-new-tokens 8 \
  --capacity 512 \
  --fixed-length \
  --output results/m1-generation.json
echo $?
```

程序使用 HF tokenizer 准备输入，之后的模型计算、KV 更新与生成循环均走自研代码。默认关闭 thinking。固定长度会在选 token 前屏蔽 EOS；去掉 `--fixed-length` 后允许遇 EOS 提前结束。输出预算很短时，文本可能是不完整的一句话，这不是程序失败。

`--capacity 512` 表示为当前请求预留最多 512 个 token 的 KV；FP16 Qwen3-0.6B 的逻辑 KV 空间为 56 MiB。容量必须覆盖 prompt 加输出预算；chat template 的特殊 token 也计入 prompt 长度。

这里报告的是**未单独预热的一次请求**，可能包含算子首次编译。此命令用于功能学习，不可直接拿其耗时和 M0 预热后的均值宣称加速。

### 预热后测量 TTFT、TPOT 和吞吐

需要性能基线时，保持同一进程，完整请求预热 1 次，再测量 3 次：

```bash
python -u -m bench.m1 \
  --model ./models/Qwen3-0.6B --device npu --dtype float16 \
  --max-new-tokens 8 --capacity 512 --fixed-length \
  --warmup 1 --runs 3 --output results/m1-warm.json
echo $?
```

每次请求都重置逻辑 KV，不复用上一次的 prompt 计算；连续 KV 的存储容量和模型在计时前准备好。`warmup_runs` 保存预热原始结果但不进入均值，`runs` 保存正式样本，`summary` 保存均值、中位数和范围。NPU 内存峰值在预热后重置一次，随后包含正式测量过程；该值不是整机共享内存用量。

```bash
python -c 'import json; d=json.load(open("results/m1-warm.json")); print(d["status"]); print(json.dumps(d.get("summary"),ensure_ascii=False,indent=2))'
```

3 个短请求用于初步比较，不证明 P99 或长上下文性能。如果正式样本还出现长时间编译等待，应标记测量未稳定，不能只删除慢样本。新增参数默认仍为 `--warmup 0 --runs 1`，保持原有单次启动行为。

## 4. 运行 HF 数值对拍

```bash
python -m bench.compare_m1 \
  --model ./models/Qwen3-0.6B \
  --device npu \
  --max-new-tokens 4 \
  --capacity 512 \
  --atol 0.01 --rtol 0.01 \
  --output results/m1-compare.json
echo $?
```

这条命令依次完成：

1. 计算权重、JSON 配置和源码哈希。
2. 用 HF eager/greedy 生成固定长度参考 IDs。
3. 把同一序列喂给 HF，保存 embedding、每层输出、最终 norm 和全位置 logits。
   同时记录 HF 自己的缓存/重算误差作为控制组，帮助识别不同矩阵形状带来的舍入差异。
4. 释放 HF 模型，再加载自研模型，用同样输入逐项比较。
5. 每步额外比较“连续缓存前向”和“完整前缀重算”。
6. 自研模型独立生成，检查输出 IDs 是否与 HF 相同。

成功需要 JSON 中 `status="ok"`、`passed=true`，所有 case 通过且输出 IDs 一致，退出码为 0。误差不通过时状态为 `failed`、退出码 1；加载或运行异常为 `error`；主动中断通常为 `interrupted`、退出码 130。

误差判断逐元素使用 `abs(actual-reference) <= atol + rtol*abs(reference)`。`0.01/0.01` 是明确记录的初始 FP16 验收参数，并非对所有长度、硬件和模型都成立的精度保证。失败时先查看首个偏差，不能为了“变绿”随意放宽阈值。

CPU 小模型单测使用 `atol=1e-5, rtol=1e-4`。完整模型的 CPU 缓存/重算可能因矩阵形状不同出现更大的舍入差；本次独立 CPU 实验在 HF 控制组观察到约 `5.05e-5` 最大绝对误差，随后用显式 `--atol 0.0001 --rtol 0.0001` 在另一 prompt 验证。CLI 的 CPU 默认仍保持严格起点；查完整 CPU 结果时应同时看 `hf_cache_vs_recompute`，不要把控制组失败隐藏掉。CPU 与 NPU 的阈值、设备和结果分别记录。

需要保留完整后端告警时，把输出同时保存：

```bash
set -o pipefail
python -u -m bench.compare_m1 \
  --model ./models/Qwen3-0.6B --device npu \
  --max-new-tokens 4 --capacity 512 --atol 0.01 --rtol 0.01 \
  --output results/m1-compare.json 2>&1 | tee results/m1-compare-output.txt
echo $?
```

`pipefail` 让管道保留 Python 的失败退出状态；不设置时，`tee` 成功可能遮住前面的失败。不要并行启动多份完整模型测试，以免影响板端共享内存和排错。

## 5. 如何读报告、判断卡在哪一步

生成结束后查看文字和实际输出数：

```bash
python -c 'import json; d=json.load(open("results/m1-generation.json")); print(d["status"]); print(d.get("text")); print(d.get("output_ids")); print(d.get("metrics")); print(d.get("error"))'
```

对拍结束后查看结论：

```bash
python -c 'import json; d=json.load(open("results/m1-compare.json")); print("status:",d["status"]); print("passed:",d["passed"]); print("stage:",d.get("stage")); print("first failure:",d.get("first_failed_comparison")); print("same IDs:",d.get("identical_output_ids")); print("error:",d.get("error"))'
```

详细数据位于 `cases[].comparisons`。`layer.0` 表示第一个 Decoder 层，`norm` 表示最终归一化，`logits` 是全位置词表分数，`cache_vs_recompute` 比较缓存与重算。`max_abs` 是最大绝对误差，`failing_elements` 是超出阈值的元素数，`top1_agreement` 只对 logits 有意义。

进程运行时可以在另一个 SSH 终端查看 `stage`：`hashing_model`、`loading_hf`、`hf_greedy`、`hf_teacher_forcing`、`loading_m1`、`m1_teacher_forcing_0` 等。阶段日志不是实时进度条；读取 JSON 恰逢写入可能失败，稍后重试。进程被强制终止或系统断电时，旧报告也可能停在 `running`。

对拍会进行额外拷贝、hook 与重算，其总耗时不代表服务性能。它证明的是相同设备、相同 dtype 下的参考一致性，不能证明 NPU 和 CPU 的完整模型数值完全一致。

## 6. 停止、退出与重新进入

- 运行中要停止：在运行命令的终端按 `Ctrl+C`，等待 Python 退出、回到 shell 提示符。
- 退出 Python 虚拟环境：运行 `deactivate`。它不删除环境，也不终止后台程序。
- 结束 SSH 连接：运行 `exit`。

```bash
deactivate
exit
```

下次新开 SSH 终端，重新执行第 1 节的三个命令。单独 `deactivate` 不会撤销已经加载的 CANN 环境变量。
