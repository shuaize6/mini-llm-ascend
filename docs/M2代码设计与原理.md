# M2 代码设计与原理：共享分页 KV 与 gather 参考注意力

> 文档先行：本文件在编码前定义范围、接口和必要验收。当前代码已实现，7 项 CPU 针对性测试通过，板端验证待完成。M1 数学和已有正确性结果作为本阶段的参照。

## 1. M2 完成什么

M1 为一个请求预留 `[1,Hkv,capacity,D]` 的连续 K/V。M2 把容量拆成固定大小的块，多个请求从同一个池中按需领取块；请求结束后归还，之后的请求可以复用这些物理位置。

本阶段实现共享块管理、每请求逻辑块表、跨块写入、gather、异常回收和内存统计。模型仍一次处理一个请求，可以交错推进多个请求的缓存，但没有批量计算、连续批处理或 HTTP 服务。也不实现共享前缀、引用计数或 copy-on-write。

这里的注意力是 **分页 KV + gather + dense 参考实现**：先取出有效 K/V，再调用 M1 的矩阵运算。它不是直接访问分页缓存的原生 PagedAttention kernel。gather 会产生额外临时张量，单请求速度可能下降。

| 文件 | 职责 |

`model.py` 的 Attention 继续通过 `write_layer()` 和 `view_layer()` 访问缓存。分页类保持 M1 的事务接口和 `length/capacity/keys` 属性，不改变 Q/K Norm、RoPE、MLP 等模型数学。

## 3. 逻辑位置如何找到物理位置

设块大小 B=4，请求 A 的块表是 `[0,2]`：

```text
A 逻辑 token：   0 1 2 3 | 4 5 6 7
A 逻辑块：          0    |    1
物理块：            0    |    2
扁平物理槽：     0 1 2 3 | 8 9 10 11
```

映射公式为：

```text
logical_block = position // block_size
offset = position % block_size
physical_block = block_table[logical_block]
physical_slot = physical_block * block_size + offset
```

物理块 1 可以属于请求 B。逻辑上连续的历史不需要在物理内存中相邻；gather 必须按逻辑顺序恢复，不能按物理块号排序。

只有请求自己的有效前缀可见。最后一块没有写满的槽位，以及别人的块，都不能进入 attention。

## 4. 块管理：分配失败不能留下半份状态

`BlockManager` 使用一个空闲队列与一个所有权字典。`allocate(owner,count)` 先检查是否有足够空闲块，再一次性转交所有权；不足时抛出 `CacheCapacityError`，空闲队列和原请求块表保持原样。`release(owner)` 一次归还该 owner 的所有块，并优先复用刚归还的块；重复释放不再次加入空闲队列。

请求不能直接释放任意物理编号。每个请求获得唯一 owner 标识，块表只来自管理器返回值；首版一个块只属于一个请求。对象不是线程安全容器，多请求交错推进由调用者串行安排。

begin_step 中申请的是新增块数：

```text
required_blocks = ceil((length + q_len) / block_size)
new_blocks = required_blocks - len(block_table)
```

请求 `capacity` 是逻辑长度上限，池的 `num_blocks` 是共享总预算，两者不同。即使未超过请求上限，也可能因其他请求占用而无法申请；M2 报错并由运行器回收当前请求，排队策略留给后续调度器。

## 5. 张量池与写入顺序

每层分配一对 `[num_blocks,block_size,Hkv,D]` 张量。整个池一次分配，各请求只保存小块表，不为自己再创建最大长度的 K/V 张量。当前 K 是经过 QK Norm 和 RoPE 后的值，V 是投影后的值，与 M1 一致。

`write_layer()` 按块边界把本次 K/V 切成片段，用切片 `copy_()` 写入对应物理块；不逐 token 启动一次小拷贝，也不要求新的 scatter 算子。若一次输入从位置 3 写入 3 个 token，B=4，则分别写“当前块的 1 个槽”和“下一块的 2 个槽”。

`view_layer()` 将池视为 `[num_blocks*block_size,Hkv,D]`，按当前有效槽索引执行 `index_select`，再变换为 `[1,Hkv,T,D]` 交给原注意力。每次 forward 的逻辑槽索引在 begin_step 生成一次，供全部层复用。

gather 输出只包括 T 个有效 token；随后 M1 自己做 GQA 扩展和 causal mask。M2 不把永久缓存扩成 Q head 数，也不让尾块未初始化数据参与计算。

## 6. 请求状态与异常边界

| 操作 | 状态变化 |
| --- | --- |
| `begin_step(q_len)` | 检查长度、申请新增块、固定 start/end、准备有效槽索引 |
| `write_layer(i,k,v)` | 校验形状、设备、dtype；本层只允许写一次 |
| `view_layer(i)` | 仅允许读取本步已写入层的有效前缀 |
| `commit_step()` | 确认所有层完成，统一更新 length；记录峰值有效 token 数 |
| `abort_step()` | 缓存标记失败，禁止继续使用；由 reset/close 回收 |
| `reset()` | 归还当前请求全部块、清空逻辑状态，保留本次峰值统计供报告使用 |
| `close()` | reset 后永久关闭该请求句柄，并移除池中的统计登记 |

与 M1 一样，当前 K/V 在层内写入，整次 forward 成功后才统一提交长度。中途某层失败不能继续把半写入缓存当作有效前缀。

运行器在请求前后 reset；EOS、输出预算结束和 Python 异常都经过 finally 回收。直接调用 `model(ids,cache)` 的学习者需要用 try/finally 关闭缓存句柄。SIGKILL、断电、设备驱动异常不属于 Python finally 能保证处理的范围。

归还块不必将所有字节清零，但新请求只能读取自己重新写入的有效区。CPU 测试会刻意复用含旧数据的块检查这一点。

## 7. 必须区分的内存数字

以 Qwen3-0.6B FP16、28 层、8 个 KV head、head_dim=128 为例：

```text
bytes_per_token = 2(K/V) * 28 * 8 * 128 * 2 = 112 KiB
bytes_per_block(B=16) = 1.75 MiB
32 blocks 的池 = 56 MiB
```

| 指标 | 含义 |
| --- | --- |
| `pool_reserved_bytes` | 实际池张量总字节数，创建时就占用 |
| `allocated_blocks` / `free_blocks` | 被请求领取与可以复用的块数 |
| `allocated_capacity_bytes` | 已领取块对应的容量，属于池的一部分 |
| `committed_tokens` / `logical_valid_bytes` | 已完成整次 forward 的有效前缀 |
| `unused_allocated_slots` | 已领取槽减已提交 token；步骤执行中也包含尚未提交的新槽 |
| `peak_gather_pair_bytes` | 一个层的一对 gather K/V 输出的最大逻辑字节数，不含 GQA、scores、allocator 对齐 |
| allocator allocated/reserved/peak | 框架的分配统计，不能当作整机内存 |

普通生成 21-token 输入、8-token 输出，最大缓存长度是 28。B=16 时请求需要 2 块，即 3.5 MiB；若池仍为 56 MiB，进程不会因此自动少占 52.5 MiB，只是剩余 30 块可供其他请求使用。

这比“分页后内存减少 93.75%”更准确。后者混淆了请求所占块容量和整个池的预留容量。

## 8. 只做必要的测试

实现前不跑大模型。实现后按以下顺序执行：

1. **一个 CPU 针对性测试文件**：块分配不足的原子性、重复释放、跨块/不连续块写入、尾块隔离、复用、两请求交错、模型中途异常和运行器 finally 回收；同时与 M1 比较同输入 logits/输出 IDs。
2. **一次板端命令**：真实权重仅加载一次，先比较非连续块布局下的 Prefill 与一次 Decode logits；再各对 M1/M2 预热 1 次、测量 3 次，复用 M1 计时公式。每轮输出 IDs 必须一致，池在请求后无占用泄漏。
3. 如果前两步通过，不重跑 M0/M1 全套或额外 HF 对拍；只有本阶段实际失败才加定位检查。

CPU 小模型使用原来的紧容差，NPU FP16 沿用 `atol=0.01, rtol=0.01`，不因分页失败而静默放宽。板端比较与性能分开计时，数值验证不混入性能样本。三个短样本只提供起始结果，不支持长上下文或高并发结论。

## 9. 学习与后续边界

先看纯 Python 块管理和 B=4 演示，再看 `PagedKVCache.begin_step → write_layer → view_layer → commit_step`。之后对照 M1 注意力，理解为何替换存储不用改模型数学。

M2 的速度可能低于连续 KV；若发生，应保留数据并解释 gather、索引传输和 Python 分块拷贝的成本。连续批处理、Prefix Cache 和原生分页 kernel 后续分开做，本阶段不为了速度提前加入这些机制。
