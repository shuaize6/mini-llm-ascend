# M2 运行与学习指南

> 代码已实现，7 项 CPU 针对性测试及一次板端验证通过。下面列出实际命令与成功条件。原理见 [M2 代码设计与原理](M2代码设计与原理.md)，已完成的性能、内存及限制见 [实验记录](experiments/m2-310b4/README.md)。已有结果可直接阅读，无需为了查看数据重跑实验。

## 1. 进入环境

以下 Bash 命令在开发板执行：

```bash
cd /root/mini-llm-ascend
source /usr/local/Ascend/ascend-toolkit/set_env.sh
source .venv/bin/activate
export MAX_COMPILE_CORE_NUMBER=2
export TE_PARALLEL_COMPILER=2
```

`command -v python` 应为 `/root/mini-llm-ascend/.venv/bin/python`。沿用已有依赖，不升级 CANN 或 torch。完整模型命令串行执行；先等上一个进程退出，再启动下一个。

## 2. 先看纯 Python 的小例子

```bash
python -m bench.demo_paged_kv
```

演示 B=4 的块分配：A 使用物理块 0，B 使用块 1，A 继续增长后使用块 2，因此 A 的块表为 `[0,2]`。A 退出后，其块可以被其他请求复用。演示不需要模型权重或 NPU。

## 3. 只运行 M2 的针对性测试

```bash
python -m unittest discover -s tests -p test_paged_kv.py -v
echo $?
```

成功时末尾应为 `Ran 7 tests`、`OK`，退出码 0。这里是 CPU 小模型和缓存行为测试，不下载大权重。本阶段不需要重复跑全部 M0/M1 测试。

## 4. 一次命令完成必要的板端验证与性能对照

```bash
set -o pipefail
python -u -m bench.m2 \
  --model ./models/Qwen3-0.6B --device npu --dtype float16 \
  --capacity 512 --block-size 16 --num-blocks 32 \
  --max-new-tokens 8 --warmup 1 --runs 3 \
  --output results/m2.json 2>&1 | tee results/m2-output.txt
echo $?
```

默认使用与 M1 相同的短 prompt、无 thinking 模板、greedy 和固定输出长度。加载一次模型，数值检查通过后，顺序运行连续缓存和分页缓存；同一时段的 M1 是本次控制组，不把旧的 7.41 token/s 直接当作当前控制组。

该验证要求输入 token 数大于块大小，以真正覆盖跨块，默认 21-token 输入与 B=16 满足要求。自定义短 prompt 时可减小 block_size；不要把未触及跨块的样例当作跨块验证。

两种缓存容量都为 512 token 的逻辑 KV，即 56 MiB；M2 请求按需领取块，池本身仍是预分配的。报告同时保存每轮 TTFT、TPOT、吞吐、allocator 内存和页池统计，避免把“已领取块减少”写成“实际预留内存下降”。

成功必须满足：数值比较通过、每个测量请求输出 IDs 与控制组一致、请求结束后池没有未归还块，最终 `status=ok`。预热不计入摘要，原始预热数据仍保存。首次新算子/shape 编译较慢，关注终端阶段日志，不额外并发运行探针。

## 5. 扩大吞吐对照（按需运行）

已完成一轮此协议，原始数据和结论见 [扩大样本吞吐对照](experiments/m2-310b4/扩大样本吞吐.md)。只想了解结果时直接阅读记录，无需重跑。

原验收每个后端只有 3 个样本、每次输出 8 token。约 4% 的均值差可能受运行波动和固定执行顺序影响，不能直接当成稳定差距。需要更充分的单请求性能数据时，执行以下一轮即可，不重复功能测试：

```bash
set -o pipefail
python -u -m bench.m2 \
  --model ./models/Qwen3-0.6B --device npu --dtype float16 \
  --capacity 512 --block-size 16 --num-blocks 32 \
  --max-new-tokens 32 --warmup 2 --runs 20 --order paired \
  --output results/m2-expanded.json 2>&1 | tee results/m2-expanded-output.txt
echo $?
```

先分别完整预热双方，再进行 20 对测量；奇数轮 M1→M2，偶数轮 M2→M1。每种实现各 20 个正式请求、640 个输出 token；两次预热不计入统计。每轮切换时在计时外重建缓存，并清理上一后端，避免两个缓存池同时驻留影响内存读数。请求内的块分配、回收和 gather 仍计时；这是一种串行交替比较协议，不代表服务连续接流时的缓存驻留行为。

保留一次短数值检查，以及每个生成请求的输出 IDs 一致性和块回收检查。新的输出 shape 首次编译可能耗时较长。`summary` 给出均值、中位数、样本标准差、最小/最大值，`aggregate_output_tokens_per_s` 是总输出 token / 总生成耗时；`pairs` 记录每对顺序及吞吐差百分比。不要把不同输出长度的旧样本混合平均，也不能用这轮单请求数据声称并发吞吐或 P99。

如何理解这些数字：

- **均值**：所有正式请求的指标相加再除以请求数；不能只选最快一轮。
- **中位数**：排序后的中间值，受单个异常慢请求的影响较小。
- **样本标准差**：描述本轮请求之间的波动，不是“误差百分比”，也不是置信区间。
- **TTFT**：从生成开始到 host 观察到第一个输出 token 的时间。
- **TPOT**：第一个到最后一个输出 token 之间的平均间隔；32-token 请求有 31 个间隔。
- **输出吞吐**：32 / 整次生成秒数，包含首 token 等待和结束时的缓存回收，因此不严格等于 1000 / TPOT。

`M2 / M1 - 1` 为负表示本轮分页实现更慢。增加样本有助于观察波动，但相同 prompt、同一台板、同一次进程仍是有限条件；不能据此推断所有输入长度和并发场景的收益。

## 6. 查看结果与退出

```bash
python -m json.tool results/m2.json
```

如果失败，查看 `status`、`stage`、`error` 和已保存的部分结果；非 0 退出码不是通过。比较吞吐时同时检查内存口径和原始样本，不能只选最快一轮。

| JSON 字段 | 如何阅读 |
| --- | --- |
| `validation.cases` | Prefill/Decode 的 logits 误差和实际块表，应出现不连续物理块 |
| `backends.contiguous.summary` | 本轮 M1 控制组的 TTFT、TPOT、吞吐 |
| `backends.paged.summary` | M2 gather 参考实现的对应指标 |
| 各后端的 `warmup_runs/runs` | 预热与正式原始样本，不能混在一起求均值 |
| 分页 `runs[].request_kv` | 本请求峰值块数、有效 token 数、gather 临时输出大小 |
| `pool_after_request/pool_after_close` | 请求结束后 allocated_blocks 应为 0，close 后请求句柄登记也应为 0 |
| `runs[].memory` | allocator 内存统计，不是整机内存用量 |

停止运行按 `Ctrl+C`，等进程退出后：

```bash
deactivate
exit
```

M2 没有常驻服务。`deactivate` 只退出 Python 虚拟环境，不停止后台进程，也不撤销当前 shell 的 CANN 环境。
