# M3 请求调度与连续批处理

## 目标与边界

每次 step 根据当前活跃请求组成批次，执行一次合并前向，每个请求产生一个 token；随后释放完成请求，下一步补入排队请求。支持运行期间 submit 和 cancel。首版为单线程、greedy、FIFO，不含 HTTP、抢占、Prefix Cache 或原生分页算子。

## 合并前向

输入为多个无 padding 的 `[1,Q_i]` 张量，按 token 维拼接为 `[1,sum(Q_i)]`。Embedding、Q/K/V 投影、输出投影和 MLP 使用合并张量。每个请求独立计算 RoPE 位置、因果 mask、读取自己的分页缓存并计算注意力，再按原顺序拼接上下文。最后仅选择各请求最后一个位置的 logits。

这样可混合新请求的 Prefill 与老请求的单 token Decode，避免 padding 位置污染；注意力仍是逐请求 dense 参考计算，不能据此承诺吞吐提升。单请求 M1/M2 路径保留用于对照。

## 状态与预算

请求状态为 waiting → running → finished，另有 cancelled / failed。输出事件包含请求 ID、token ID、是否结束及结束原因。cancel 同步释放缓存，重复取消无副作用。close 取消剩余请求；调度器不负责释放外部持有的池张量。

请求最大实际 KV 长度为 prompt_length + max_new_tokens - 1，准入信用为其向上取整的块数。所有活跃请求信用总和不超过池容量；真实块仍按需分配。此保守策略避免多个活跃请求各占部分块后互相等待，代价是长预算请求降低准入率。FIFO 队首暂时不能进入时，后续请求等待，不插队。单个超出池容量的请求在 submit 时拒绝。

池由调度器独占，外部不应从同一池分配缓存。批内步骤失败时，关闭整个活跃批次并标记 failed，向调用方抛出异常；排队请求保留。批内采样全部成功后才发布本步 token，防止只发布半个批次。

## 必要验证

CPU 小模型验证变长混合批次 logits 对拍、动态补位、EOS、取消、预算排队和错误回收。随后只运行一次板端短批次对照，与 M1 独立请求比较输出。CPU 通过不能冒充 NPU 通过；本版不预设性能收益。

`forward_batch()` 先验证所有输入，再逐个 begin_step。每层只执行一次合并 Q/K/V 投影，用 offset/end 切出每个请求的片段；各自的 mask 和缓存决定可访问的历史，不能在拼接后的全部 token 上直接做一次无隔离注意力。各请求上下文按输入顺序重新拼接，再共享输出投影与 MLP。所有层成功后提交缓存长度；异常时已开启的事务全部 abort，调用者负责 close。

例：A 已有 5 个 KV token，本步 Decode 1 个；B 新请求 Prefill 3 个。打包长度为 4，A 的位置是 `[5]`，B 的位置是 `[0,1,2]`。A 注意力范围是自己的 6 个 KV token，B 是自己的 3 个；最终只取打包位置 0 和 3 的 logits。不能给 B 使用位置 6，也不能让 B 访问 A 的缓存。

`submit()` 验证预算并复制输入，尚不申请 KV 块。`step()` 先准入，再选输入：尚无输出的请求使用整个 prompt，已有输出的请求只输入上次生成的最后一个 token。全部采样成功后发布 TokenEvent；命中 EOS 或输出预算时 close。下一次 step 才补位，因此到达/取消发生在步骤边界，没有线程抢占。

信用示例：池有 4 块，A 最大需要 3 块，B 最大需要 2 块。即使 A 当前只领取 1 块，也先让 B 排队；A 完成后 B 入场，避免之后 A、B 同时扩容导致资源不足。这个策略用利用率换取简单且能推进的资源约束，不宣称已实现最优调度。

`cancel()` 对排队与运行中的请求均有效。重复取消返回 False；不存在的 ID 抛出 KeyError。`close()` 可重复调用，取消所有尚未终止的请求；关闭后不能 submit 或 step。返回的 Request 供读取结果，调用方不要直接修改其状态、cache 或 output_ids。首版保留历史请求，长期服务应补充队列限额与历史清理。
