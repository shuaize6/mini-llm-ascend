# M2 验证与性能记录

日期：2026-10-31。实现提交：`2f18d97`。本阶段按“先文档 → 实现 → 必要测试”的顺序完成，设计文档初稿提交为 `0a0445c`。

M2 实现共享分页 KV 池、每请求块表、跨块写入、gather 参考注意力和回收；模型数学保持 M1 路径。当前没有连续批处理、Prefix Cache 或原生分页 attention kernel。

## 本轮只做了哪些测试

1. 运行一次 `test_paged_kv.py`，**7 项 CPU 针对性测试全部通过**，测试运行器耗时 0.101 秒。本机环境与命令见 [测试执行记录](cpu-test-record.json)，该文件是本次已观察结果的归档，没有为生成记录重复执行测试。
2. 运行一次板端 `bench.m2`：真实权重加载一次，进行两项 M1/M2 数值比较，再对两个后端分别预热 1 次、测量 3 次。

没有重跑 M0/M1 全套测试，没有重新加载 HF 做逐层对拍，也没有因为 M2 没有变快而追加重复测量。

CPU 测试覆盖：块不足时分配原子性、重复释放、跨块和不连续块、未初始化尾槽、旧块复用、两请求交错、层内异常、EOS/回调异常/池不足后的回收，以及与 M1 的 logits 和输出 IDs 一致性。

## 板端正确性

设备为 Ascend 310B4；沿用板载 torch 2.1.0 / torch_npu、CANN 8.1.RC1，FP16，编译并行度为 2。权重 SHA256 为 `f47f71177f32bcd101b7573ec9171e6a57f4f4d31148d38e382306f42996874b`。

验证时预留物理块 1，让目标请求使用 `[0,2]`，而不是恰好连续的块。两种缓存使用同一模型、同一输入，比较每次 forward **最后位置的全词表 logits**，没有重复逐层或全位置 HF 对拍：

| 案例 | KV 长度 | 物理块表 | logits 最大绝对误差 | top-1 一致率 |
| --- | ---: | --- | ---: | ---: |
| 跨块 Prefill | 21 | `[0,2]` | 0 | 100% |
| Decode | 22 | `[0,2]` | 0 | 100% |

容差保持 `atol=0.01, rtol=0.01`。两种后端所有预热及正式生成的 8 个输出 IDs 一致。分页请求结束后 allocated_blocks 为 0；close 后 request_handles 为 0。验证范围限于已记录短输入及 CPU 边界案例，不代表任意长度、并发或驱动版本均已验证。

原始证据：[完整 JSON](m2.json)、[终端日志](m2-output.txt)。源码指纹已逐文件核对，与提交 `2f18d97` 一致。原有 storage_offset / AutoNonVariableTypeMode 等后端告警保留在日志中，不能因本次对拍通过就宣称它们已经被根除。

## 同一进程的预热后性能

输入 21 token、固定输出 8 token、greedy、关闭 thinking；每个后端独立完整预热 1 次，再测 3 次。控制组是本次 M1，不能直接用历史 7.41 token/s 替代。

| 后端 | TTFT（ms）均值 | TPOT（ms/token）均值 | 输出吞吐（token/s）均值 | 吞吐范围（token/s） |
| --- | ---: | ---: | ---: | ---: |
| M1 连续 KV | 137.80 | 137.13 | **7.287** | 7.196～7.356 |
| M2 分页 + gather | 146.95 | 142.48 | **6.997** | 6.691～7.258 |

**本轮 M2 吞吐均值比 M1 低约 4.0%，没有加速证据。** 样本少、范围存在重叠、后端执行顺序固定，因此不把 4.0% 当作稳定减速比例。gather、索引和分块拷贝确实是实现中的额外工作，但本轮没有进行 profiling，不能把全部差异精确归因到某一项。

M1 和 M2 的预热分别耗时 26.06 秒与 102.70 秒，包含首次形状/算子编译等待，不计入上述均值。计时包括生成循环、host token 观察、请求内块申请/释放和 gather；不包括模型加载、输入准备、初始 KV 池分配及报告统计。没有混入数值对拍用的同步和张量比较。

## 内存与块复用

两种实现的逻辑 KV 预算相同，都是 512 token、56 MiB。不是给分页方案更小的池后宣称同条件内存优化。

| 指标 | 本轮结果 |
| --- | --- |
| M1 连续 KV 预留 | 56 MiB |
| M2 全局页池预留 | 32 块 × 16 槽 = 56 MiB |
| M2 本请求峰值领取 | 2 块，即 3.5 MiB 容量 |
| 有效 KV 峰值 | 28 token，即 3.0625 MiB |
| 本请求尾块未用槽 | 4 token，即 0.4375 MiB |
| 请求峰值时可供其他请求使用的块 | 30 块，即 52.5 MiB |
| 单层一对 gather K/V 输出的逻辑峰值 | 112 KiB，另有最多 224 B 的槽索引 |
| 每个请求结束后 | 32 块全部归还，可再次分配 |
| 两后端 allocator peak allocated | 均为 1,301,933,568 B，约 1.21 GiB |
| 两后端测量后 allocator reserved | 均为 1,321,205,760 B |

最后一个生成 token 未再次前向，故实际 KV 高水位为 `21+8-1=28`。单层 gather 统计不含 GQA 扩展、attention scores、分配器对齐或所有层累计搬运量。

这证明了**本请求按需领取与归还块**，没有证明本轮进程实际预留内存下降：全局池仍占 56 MiB，两种实现的 allocator 峰值也相同。空闲块能被其他请求复用的机制由交错/释放复用测试验证，但本阶段没有测多请求吞吐或更高并发容量。

```bash
  --model ./models/Qwen3-0.6B --device npu --dtype float16 \
  --capacity 512 --block-size 16 --num-blocks 32 \
  --max-new-tokens 8 --warmup 1 --runs 3 \
  --output results/m2.json
```
