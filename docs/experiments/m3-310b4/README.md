## 本轮验证

只运行一次新增 CPU 文件 `python -m unittest discover -s tests -p test_scheduler.py -v`：6 项通过，测试运行器耗时 0.188 秒。覆盖合批 logits、动态加入补位与独立生成对拍、EOS、取消、保守容量准入、批内层失败后的回收及等待队列继续推进。未重跑 M0/M1/M2 测试套件。

随后运行一次板端 `bench.m3`，Ascend 310B4、Qwen3-0.6B、FP16。使用 tokenizer 输出的 1/2-token 前缀和 1～3-token 输出，只检验短批次正确性；不是完整对话质量或性能测试。首次新形状编译较慢，本轮未测量吞吐。

| 两个不同长度请求 Prefill | `[2,1,151936]` | 0 | 100% |
| 不同历史长度、不同本步输入长度 | `[2,1,151936]` | 0 | 100% |

比较各请求最后位置的全词表 logits，FP16 容差为 `atol=0.01, rtol=0.01`。没有重新进行 HF 逐层对拍，也不将短案例零误差推广到任意输入。

## 动态批次

| 步骤 | 参与请求 | 变化 |
| --- | --- | --- |
| 1 | A | A 先生成一个 token，之后提交 B、C |
| 2 | A、B | B 输出预算为 1，完成并退出；C 等待 |
| 3 | A、C | C 补位，A 达到 3-token 预算完成 |
| 4 | C | C 达到 2-token 预算完成 |

A 输出 `[198,106287,3837]`，B 输出 `[14582]`，C 输出 `[198,106287]`，分别与 M1 独立生成完全一致。结束后 8 块全部空闲，`allocated_blocks=0`、`request_handles=0`。取消、EOS 和注入错误主要由 CPU 测试覆盖，此次 NPU 用固定长度生成验证正常路径。
