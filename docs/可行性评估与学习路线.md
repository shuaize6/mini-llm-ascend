# 可行性评估与学习路线

评估日期：2026-10-30。目标：做一个能解释、能复现、能作为 AI Infra 简历项目的轻量推理引擎。

## 1. 结论与证据边界

**建议立项，按阶段验收；当前已完成方案准备，尚未完成板端可运行性验证。**

项目定位：面向昇腾 310B 的教学型 LLM 推理与服务引擎。最值得展示的是 KV 内存管理、动态调度、性能分析和软硬件适配。Qwen3-0.6B 的规模适合验证这些机制；模型小不妨碍系统设计的价值。

本次实际检查了技术设计、README、配置、部署脚本和 Git 状态，并查阅了官方模型配置及依赖源码。仓库已有 Git 历史和目录骨架，但没有推理核心、基准或测试实现；已配置的远端名称只有 `board`。

原设计中的 1.55 TFLOPS、RMSNorm 5.09×、算子可用性等均属于既有文档记载。本次没有连接开发板复测，也未获得这些测量的完整原始日志，不能将它们视为本次验证结果。工具文件存在也不等于目标算子已能编译、运行。

## 2. 首版范围

| 层级 | 内容 | 完成证据 |
| --- | --- | --- |
| 必做 | 环境探测、HF 基线、手写 Qwen3 前向、连续 KV cache | 固定输入下的 logits 对拍、逐 token 解码、可复现命令 |
| 必做 | 分页 KV 管理、gather 参考注意力、连续批处理 | 块分配/释放正确、无串请求、请求动态加入退出、内存与吞吐曲线 |
| 必做 | 简单流式服务、取消/超时回收、基准报告 | 客户端可调用、资源能回收、原始结果可追溯 |
| 第二阶段 | Chunked Prefill、Prefix Caching | 混合负载延迟曲线、前缀复用正确性及收益 |
| 深入方向 | 根据 profiling 选择一个 AscendC 热点算子 | 与参考实现对拍，算子耗时和端到端收益分别报告 |
| 延后 | 投机解码、W8A16、完整 PagedAttention kernel、多种抢占策略 | 主线稳定且已有瓶颈证据后再投入 |

适合推理系统/Serving 方向的首版不必等到完整 kernel 完成。若主攻算子优化岗位，则至少需要一个经过正确性验证、分析过 tiling 和内存访问的 AscendC 算子。

## 3. 原设计应修正的重点

1. **生态支持范围不能写成绝对结论。** vLLM-Ascend v0.30.0 的官方安装资料包括 310P 路线，不能写“只支持 910B/910C”。该支持列表未列出本项目的 310B4 开发板；310P 支持不能外推到 310B。“自研是唯一可行路径”“唯一可用版本”应改成当前环境与项目目标下的选型结论。[官方安装资料](https://github.com/vllm-project/vllm-ascend/blob/v0.30.0/docs/source/getting_started/installation.md)

2. **依赖兼容性是首个验收关卡。** Qwen3 官方要求 Transformers 至少 4.51.0。4.57.6 的源码版本门槛允许 torch 2.1.0，但这不证明 Qwen3 全链路与板载 torch_npu 兼容。可先验证固定版本 4.51.3、eager attention、safetensors 加载，再锁定完整依赖；不要直接升级板载 torch/CANN。[模型说明](https://huggingface.co/Qwen/Qwen3-0.6B)；[4.57.6 检测源码](https://github.com/huggingface/transformers/blob/v4.57.6/src/transformers/utils/import_utils.py)

3. **分页尾块浪费与 dense padding 是两件事。** 每请求最后一块的浪费最多为 `block_size - 1` 个槽；批量 gather 后 padding 到最长序列的浪费为 `B * max_len - sum(seq_lens)`。长度 16 和 2048 的两请求会产生 2032 个 padding 槽，远大于 15。分桶或后续 kernel 才可能降低此开销。

4. **分页管理不自动带来更快的注意力。** gather 路线首先用于证明块管理正确，可能增加拷贝和临时内存。应称为“分页 KV + dense 参考注意力”，与直接访问分页缓存的原生 PagedAttention kernel 区分。

5. **当前 token 的 K/V 必须参与当前层注意力。** 每层投影、Q/K Norm、RoPE 后写入当前 K/V，或将它们显式拼入可见 K/V，再执行注意力。不能把所有 KV 写入统一推迟到 sample 之后。采样出的新 token 在下一轮前向时才产生自己的 K/V。

6. **Chunked Prefill 不能只靠 position_ids 隔离请求。** chunk 必须读取已有前缀 KV，并使用带历史长度偏移的 causal mask；批内不同请求要显式隔离。首版可分别执行 prefill 与 decode 子批次，不必立即实现统一混合 kernel。

7. **Prefix Cache 要定义复用边界。** 先仅共享完整块，key 包含模型身份、影响 KV 的配置与完整前缀关系；明确冲突处理、引用计数、逐出失效。部分块以后再引入 copy-on-write。若完整 prompt 命中但没有保存最后位置的 logits，需要重算最后 token 或设计相应结果缓存。

8. **内存池从小开始。** 按官方配置，FP16 KV 每 token 为 `2 * 28 * 8 * 128 * 2 = 114688 B`，block=16 时每块 1.75 MiB。2/4/8 GiB 分别可容纳 1170/2340/4681 个完整块，即 18720/37440/74896 个 token。首轮用约 256 MiB～1 GiB 池、并发 1～4、上下文上限 512～2048，再根据实测扩容；共享内存还要容纳加载峰值、激活和 gather 临时张量。[官方配置](https://huggingface.co/Qwen/Qwen3-0.6B/blob/main/config.json)

9. **微基准条件不能替代端到端证据。** NPU 异步执行需要明确同步与计时边界，先预热再统计。单算子倍数不能直接换算成模型倍数；若热点占比为 p、该算子加速为 s，理想整体加速上限为 `1 / ((1-p) + p/s)`。

10. **AscendC 工程还有真实集成成本。** pybind11 + aclnn 仍需处理 NPU Tensor 的地址/格式、当前 stream、workspace 和异步生命周期。先验证最小算子的编译、上板与 torch 调用链，再投入 K1/K2。当前 KV 布局中单个 head 跨 token 存储不连续，不能把 K2 的 DataCopy 伪代码当成已确定的搬运方案。

11. **验收不要预先承诺速度。** 2.5× 吞吐、10% TPOT 降幅、50% 前缀命中率都只能作为实验假设。20 次请求的 P99 不稳定，应展示样本数并增加持续负载测量。W8A16 的理论权重体积减半也不代表实际峰值内存减半；反量化会产生额外数据搬运。ATC 离线图优化不能直接当作 eager torch_npu 路径的融合开关。

## 4. 便于学习的代码约定

- 英文标识符配中文说明。注释解释设计原因、输入输出、张量 shape 和状态变化，避免逐句翻译代码。
- 先写直观参考实现，再增加优化分支；两条路径使用相同输入进行对拍。
- 调度和块管理尽量写成普通 Python 与 dataclass，不依赖 NPU，便于本机运行和测试。
- 模型数学与设备调用分开，torch_npu 延迟导入；CPU 路径用于正确性，不与 NPU 路径做性能排名。
- 不提前引入复杂继承、插件注册、分布式抽象；一个模块围绕一个清晰职责。
- 每阶段提供一个最小示例、一份阅读顺序、一组必要测试和一段实验解释。阶段提交必须可运行，不一次倾倒整个系统。
- 性能优化前先回答“慢在哪里”，优化后解释“为什么有效或无效”。

建议阅读顺序：`model → contiguous_kv → block_manager → paged_attention_reference → scheduler → engine → server → benchmarks → ascendc`。这些是后续实现职责，当前并非已存在的可运行模块。

推荐教学例子：用 block_size=4 的小缓存手工追踪两个请求，逐步打印逻辑块号、物理块号、slot、引用计数与释放事件；再切换到真实模型的 block_size=16。

## 5. 分阶段推进与停止条件

| 阶段 | 先做什么 | 通过后再做什么 |
| --- | --- | --- |
| A：可运行性 | 记录环境、验证张量操作、加载 Qwen3、跑短 greedy generation | 锁版本与模型 revision，保存原始日志 |
| B：正确性 | 单请求前向、连续 KV、逐层/整模型对拍 | 再替换为分页 KV |
| C：系统机制 | 块管理、批处理、请求生命周期 | 接流式服务和性能基准 |
| D：分析优化 | 测量长短请求混合负载，找瓶颈 | 加 chunked prefill、prefix cache 或一个热点算子 |
| E：可展示交付 | 复现报告、架构图、实验数据、限制说明 | 发布版本并据实写简历 |

A 阶段是继续 NPU 路线的关卡：导入、权重加载、算子和短生成必须实际通过。若 HF 在板上失败，可在单独兼容环境导出参考结果，板上逐层对拍手写前向；这只能提供正确性参考，不能冒称同平台 HF 性能基线。若目标算子仍无法运行，应缩减后端或模型范围，并明确记录未通过之处。

B 阶段先使用 FP32 CPU 小输入定位数学错误，再验证 FP16 NPU。同时报告 max/mean 绝对误差、相对误差、top-1 一致率；阈值结合参考后端误差确定，不能仅靠生成文本“看起来正常”。

C 阶段首版 KV 不足可先排队/拒绝，设定超时与公平性边界；不用立即实现 swap。必须验证跨块边界、块复用、请求取消、异常退出、内存不足和不同长度请求之间无数据污染。

## 6. 简历证据与公平测量

真正可写进简历的成果应同时包含：实现、正确性证据、可复现数据、技术取舍。

- 基线至少包含 HF 单请求、HF 静态批处理（若同环境可运行）、自己的单请求引擎、自己的连续批处理引擎。
- 统一硬件、模型 revision、dtype、tokenizer、chat template、thinking 开关、采样方式、输入输出长度、EOS 策略和并发/到达率。
- 区分模型执行耗时与客户端请求延迟；客户端 TTFT 包含排队、分词、prefill 和传输。报告吞吐、TTFT、TPOT/ITL、完成数、失败数和内存峰值。输出少于两个 token 时 TPOT 不适用。
- 区分 KV 池预留、已分配块、有效 token、尾块空洞、gather/padding 临时内存。只展示池使用率不能证明节省内存。
- 性能报告保存命令、Git commit、环境、工作负载、原始数据和汇总结果；负收益也保留。

完成后的简历表述可围绕“在昇腾 310B 实现分页 KV 与连续批处理，支持流式请求与取消回收，在固定负载下报告吞吐/延迟/内存改善”组织。未做的 kernel、不存在的性能数字以及 CPU 结果都不能冒充板端成果。
