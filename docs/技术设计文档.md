# NanoServe-Ascend 技术设计文档

> 面向昇腾 310B4（香橙派 AIpro 8T）的手写轻量 LLM 推理引擎
> 技术路线：**混合栈** —— torch_npu 主引擎 + AscendC 原生算子模块
> 目标模型：Qwen3-0.6B ｜ 版本 v0.2（设计阶段） ｜ 2026-10-30

---

## 1. 项目概述

### 1.1 背景

vLLM 是当前 LLM 服务的事实标准，但其 NPU 后端（`vllm-ascend`）只覆盖 910B/910C 数据中心卡。边缘侧昇腾 310B4（香橙派 AIpro / Atlas 200I DK A2 同款芯片）算力约 1.5 TFLOPS（fp16，实测）、显存与主机内存共享 16 GB，既没有 PagedAttention kernel，也没有 FlashAttention 的 paged 变体。

本项目的目标是：**在这样一块"残缺"的国产 NPU 上，把 vLLM 的核心机制手工实现一遍**，并在算子层下沉到昇腾原生编程模型（AscendC），给出可复现的性能数据。

它由两层构成：

- **上层（系统）**：分页 KV cache、连续批处理、前缀缓存、投机解码、OpenAI 兼容服务 —— 用 PyTorch + torch_npu 实现，追求迭代速度。
- **下层（算子）**：把 decode 阶段最热的算子用 AscendC 写成原生 kernel，绕过"没有 paged 注意力算子"的限制，追求性能上限。

### 1.2 目标

| # | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | 手写 Qwen3-0.6B 前向 + KV cache，输出与 HF 实现对齐 | logits 最大绝对误差 < 1e-2（fp16） |
| G2 | 实现 PagedAttention（块池 + block_table + gather 注意力） | 相对"按请求预分配"的内存占用对比表 |
| G3 | 实现 Continuous Batching 与 Chunked Prefill | 并发 1/2/4/8 的吞吐曲线 |
| G4 | 实现 Prefix Caching | 多轮对话场景的命中率与前缀复用收益 |
| G5 | 实现投机解码（prompt-lookup 优先） | 平均接受长度 τ 与端到端加速比 |
| G6 | 实现 W8A16 权重量化 | 显存占用与 TPOT 变化（正负都要报） |
| G7 | 算子融合优化与消融实验 | 4 组配置的 TTFT/TPOT 对比 |
| G8 | OpenAI 兼容流式 API | `curl` 流式输出，P99 TTFT 有数 |
| **G9** | **AscendC 原生 kernel 替换 torch 实现** | **kernel 级耗时对比 + 端到端 TPOT 降幅（目标 ≥10%）** |

### 1.3 非目标（明确排除，避免范围蔓延）

- 不做训练/微调。
- 不做张量并行、流水并行（单卡无意义）。
- 不做真 W8A8（需要 ATC/AMCT 离线量化或 AscendC 量化算子的完整工程，作为后续工作）。
- 不与 vLLM 做横向对比（平台不可比），只与 **HuggingFace `generate` 基线** 对比。
- 不追求"超越 vLLM"，只追求"在受限平台上做出正确取舍并量化其代价"。

### 1.4 简历价值

差异化不在"跑通一个大模型"，而在于**在资源受限的国产 NPU 上，从调度层一路做到算子层**：

- 系统侧：分页 KV cache 的内存布局与碎片消除（含具体字节数计算）、连续批处理调度器状态机、前缀缓存的块级哈希、投机解码的接受率建模
- 算子侧：**用 AscendC 手写 kernel**，理解昇腾的 GM/UB 内存层次、tiling 切分与双缓冲
- 取舍侧：在带宽受限芯片上量化收益边界的实测分析（W8A16 不划算也如实报告）

### 2.2 算力实测

```text
torch 2.1.0 | torch_npu 2.1.0.post2 | 设备 Ascend310B4
```

### 2.4 为什么不用现成 vLLM（评估结论存档）

| 包 | 依赖要求 | 与本环境冲突 |
| --- | --- | --- |

| `vllm-ascend` 0.9.2rc1（有 cp39 轮子） | `torch_npu 2.5.x`、CANN ≥ 8.0、910 系硬件 | torch_npu 2.1.0.post2 不可替换；310B 不在支持列表 |
| `vllm` 0.32.0（CPU 后端） | `torch==2.13.0` | 与 torch_npu 2.1.0 冲突，且不使用 NPU |

结论：**自研是唯一可行路径**。

### 2.5 网络限制（影响部署方式）

板子仅能访问 PyPI 镜像（清华源），**无法访问** HuggingFace / ModelScope / hf-mirror / gitee（TCP 超时）。因此：

- 模型权重与第三方包：**笔记本代理下载 → `scp` 传输**（实测 1.4 GiB 上传约 60~110 秒）。
- 运行期不依赖外网（推理引擎离线可跑），这对"边缘部署"是加分项。

## 3. 技术栈选型与昇腾生态评估

### 3.1 问题

"必须用 torch 吗？昇腾有没有专属生态能做这件事？"

结论：**不是必须**，但在这块板子上，"专属生态"能提供的现成能力比想象中少。下面是逐项实测结果。

### 3.2 昇腾原生组件盘点（全部在板上验证过）

| 技术栈 | 板上是否存在 | 关键发现 | 能否提供 paged 注意力 |
| --- | --- | --- | --- |
| **MindSpore 2.6.0** | ✅ 已装 | Python 层有 `ops.PagedAttention` / `ops.PagedAttentionMask` 接口，但 310B 的 ai_core kernel 目录（211 个算子）**没有对应实现** | ❌ 仍需手写 |
| **C++ ACL / aclnn** | ✅ 齐全 | `include/acl/*.h`、`libaclnn_ops_infer.so` 等；aclnn 无 paged attention 接口 | ✅ 可自写，但需自己拼 |
| **AscendC 自定义算子** | ✅ **可用** | `bisheng`（clang 15.0.5）、`kernel_operator.h`、`tikcpp`、`msopgen`、`ascendc_kernel_sample`、`tikicpulib`、`msdebug`、`mssanitizer` 全部就位 | ✅ **可自己写 kernel** |
| **ATB**（Transformer Boost） | ❌ 不存在 | 无 `libatb*`；昇腾 LLM 加速库只覆盖 910/310P | — |
| **MindIE**（华为推理引擎） | ❌ 不存在 | 仅支持 910 系 | — |
| **MindSpore Lite** | ⚠️ 可装，但只有 CPU | 官方 aarch64 tar.gz 存在（57.6 MB，含 `converter_lite` / `benchmark` / `libmindspore-lite.so`），**但无 Ascend 后端插件、无 Python 绑定**；PyPI 仅 2.0.0 的 x86_64 轮子 | ❌ 纯 CPU，用不上 NPU |

### 3.3 逐项排除理由

- **MindSpore**：作为"框架层"与 torch_npu 对等，但**没有算子层优势**——`ops.PagedAttention` 只是 Python 接口，310B 的 opp 里没有 kernel，跑起来会报找不到算子。换过去等于重写一遍调度器，收益为零。
- **ATB / MindIE**：昇腾面向大模型的加速库与推理服务引擎，硬件支持列表中都没有 310B（边缘芯片被排除在数据中心工具链之外）。
- **MindSpore Lite**：面向端侧的**推理 runtime**（`converter_lite` 把 MindIR/ONNX 转成 `.ms`，`libmindspore-lite.so` 执行），主打小体积与量化，典型场景是固定 shape 的视觉模型。PyPI 上只有 2.0.0 的 x86_64 轮子（跨架构二进制不能靠拷贝解决），但官方另提供 `mindspore-lite-2.6.0-linux-aarch64.tar.gz`（57.6 MB），解压即用、不需要 pip。**问题在于这个包只带 CPU 后端、没有 Ascend 插件，也没有 Python 绑定**；要用 NPU 需带 CANN 从源码编译。更本质的是——它是 runtime 而非 serving engine，不提供 paged KV / 连续批处理 / 前缀缓存，无法承担本项目 M2~M7 的内容，故不采用（其 `benchmark` 工具最多作为 CPU 侧对照，不进入主实验）。
- **C++ ACL**：完全可行，但纯 C++ 写调度器迭代成本极高，且 aclnn 里同样没有 paged 注意力，仍需自己实现。

### 3.4 为什么 torch 版本被锁死在 2.1.0

- 板上 `torch_npu 2.1.0.post2` 是**针对 310B 编译的唯一可用轮子**（`/opt/pytorch/dist/*.whl`，源码树也在 `/opt/pytorch`）。
- 升级到 torch_npu 2.5+ 需要同时满足 CANN ≥ 8.0 与 910 系硬件假设；实测 CANN 8.5.0 在 310B 上会因 HCCL 配置项缺失导致初始化失败（已在 MindSpore 路径上复现）。
- 因此"用 torch 2.1.0"是**平台约束下的唯一解**，不是技术偏好。

### 3.5 选型结论：混合栈

| 层 | 技术 | 理由 |
| --- | --- | --- |
| 调度 / 缓存 / API | PyTorch + torch_npu | 迭代快；能拿到 1.55 TFLOPS；生态成熟（便于对拍与调试） |
| 热点算子 | **AscendC 自定义 kernel** | 唯一能真正吃到"昇腾原生"红利的层面；也是简历含金量最高的部分 |
| 对照实验 | 框架融合算子（`npu_rms_norm` 等） | 提供"框架层融合 vs 手写 kernel"的量化对比 |

**关键判断**：系统层的工程能力用 Python 体现，算子层的芯片理解用 AscendC 体现，两者互补而非冲突。

- **Prefill 计算密集**：FLOPs ≈ 2·P·S。S=512 时约 610 GFLOP，理论 0.39 s（≈1300 tok/s），预期实际 300~600 tok/s。
- **Decode 访存密集**：每 token 需完整读一遍权重（1.11 GiB），单步耗时下限 = (权重 + KV) / 有效带宽。
- bf16 与 fp16 均可用（已实测），默认 fp16。

## 5. 总体架构（混合栈）

### 5.1 分层图

```text
┌──────────────────────────────────────────────────────────────────┐
│  Python 层（torch_npu）                                          │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │ api/server.py       FastAPI · OpenAI 兼容 · SSE 流式       │  │
│  ├────────────────────────────────────────────────────────────┤  │
│  │ engine/scheduler.py  连续批处理 · chunked prefill · 抢占    │  │
│  │ cache/               块管理 · 前缀哈希 · 引用计数           │  │
│  │ engine/model_runner.py  Qwen3 前向（含 q/k-norm）           │  │
│  │ engine/sampler.py    采样                                  │  │
│  └───────────────┬────────────────────────────┬───────────────┘  │
└──────────────────┼────────────────────────────┼──────────────────┘
        调用 torch_npu 算子              调用自定义算子（可选开关）
                   │                            │
┌──────────────────▼───────────┐  ┌─────────────▼──────────────────┐
│ 框架层融合算子                │  │ AscendC 原生 kernel 模块        │
│ npu_rms_norm / rotary_mul /  │  │ K1: QK-Norm + RoPE 融合         │
│ npu_fusion_attention         │  │ K2: PagedAttention Decode       │
└──────────────────────────────┘  └─────────────┬──────────────────┘
                                                │ pybind11 → aclnn
┌───────────────────────────────────────────────▼──────────────────┐
│ CANN 8.1.RC1 · AscendC · bisheng 15.0.5 · AI Core (310B4)        │
└──────────────────────────────────────────────────────────────────┘
```

### 5.2 单步执行流程（Step）

```text
1. schedule()      : 选出本步要跑的请求集合 + 每个请求的 token 数
2. build_batch()   : 拼 input_ids / positions / block_tables / slot_mapping
3. forward()       : 一次前向，得到 logits（只取每请求最后一个位置）
   ├─ prefill 段：dense 注意力（npu_fusion_attention 或 K2 的 prefill 分支）
   └─ decode 段 ：paged 注意力（torch gather 版 或 K2 kernel，可切换）
4. sample()        : 逐请求采样（NPU top-k，CPU 兜底）
5. append_kv()     : 新 token 的 K/V 写入 slot
6. post_process()  : 判停、回收块、上报指标
```

### 5.3 双实现开关（保证可交付）

所有下沉到 AscendC 的算子都保留一份 torch 参考实现，用配置项切换：

```text
NANOSERVE_KERNEL_MODE = torch | ascendc | auto
# auto：kernel 可用则用 kernel，不可用自动回退并记录告警
```

意义：**kernel 写不完或调不通时，项目依然是完整可运行的系统**，只是少了算子层加分项。

## 6. 关键设计

### 6.1 PagedAttention（torch 实现）

#### 6.1.1 内存布局

```text
k_cache: [num_layers, num_blocks, block_size, num_kv_heads, head_dim]   fp16
v_cache: [num_layers, num_blocks, block_size, num_kv_heads, head_dim]   fp16
```

层在最外层便于逐层切片；块维度独立，实现"任意逻辑块 → 任意物理块"的映射。

#### 6.1.2 块表与写入

```python
block_table: List[int]      # 逻辑块号 → 物理块号
seq_len: int

slot = block_table[seq_len // block_size] * block_size + (seq_len % block_size)
k_cache[layer].view(-1, kv_heads, head_dim)[slot] = k_new
```

#### 6.1.3 读取与注意力计算（三种路径）

| 方案 | 实现 | 优点 | 缺点 | 采用 |
| --- | --- | --- | --- | --- |
| A. 每请求循环 gather | 逐请求切连续 KV | 无 padding 浪费 | 循环次数 = batch，启动开销大 | 否 |
| B. 批量 gather + padding | 一次 `index_select`，padding 到 `max_len` | 单次大 kernel | 最多浪费 `block_size-1`/请求 | **torch 版采用** |
| C. 自写 kernel 直读块池 | K2（见 §6.7） | 无 gather 拷贝、无 padding | 开发成本高 | **目标方案** |

### 6.2 Continuous Batching 调度器

#### 6.2.1 状态机

```text
WAITING ──(有预算)──▶ PREFILL(chunk) ──▶ DECODE ──▶ FINISHED
   ▲                      │                 │
   └──────────────────────┴──(KV 不足被抢占)──▶ SWAPPED
```

#### 6.2.2 每步调度算法

```text
budget = max_num_batched_tokens            # 默认 2048
1. 为 running 中每个请求预留 1 token（decode 优先，保证 TPOT 稳定）
2. 剩余预算按 FIFO 分给 waiting 请求做 prefill，单请求单步 ≤ chunk_size（512）
3. 预算不足以分配新块时：抢占 seq_len 最长且最久未活跃的请求（swap 或 recompute）
4. 组装 batch，用 position_ids 区分 prefill / decode 段
```

### 6.3 Prefix Caching

```text
block_hash[0] = hash(block_tokens[0])
block_hash[i] = hash(block_hash[i-1], block_tokens[i])
```

- 相同哈希 ⇒ 相同前缀 ⇒ 物理块只读共享（`ref_count++`）
- 请求结束 `ref_count--`；归零后进 LRU 空闲队列，**块内数据保留**以支持后续命中
- 指标：`prefix_hit_tokens / total_prompt_tokens`

| 场景 | 预期命中率 |
| --- | --- |
| 多轮对话（同 system prompt） | 60~85% |
| RAG（共享文档上下文） | 40~70% |
| 独立请求 | 0%（仅一次哈希开销） |

### 6.4 投机解码（Speculative Decoding）

**方案 A：Prompt Lookup（优先实现）** —— 无草稿模型，从已生成文本中找最近 n-gram 续写作为草稿，一次前向并行验证，接受最长一致前缀。正确性严格等价于目标模型贪心。指标：接受长度 τ。

**方案 B：草稿模型（可选）** —— 需词表对齐与接受率测优；310B 上验证前向本身昂贵，接受率不足会反变慢，**先测再定**。

**与分页的交互**：一次验证 m 个 token 需预留 m 个 KV 槽，只接受 j 个则回滚 `seq_len -= (m-j)`，块管理器需支持"预留-提交/回滚"。

### 6.5 INT8 量化（W8A16）

- 仅权重量化，per-output-channel 对称：`w_int8 = round(w/scale)`，`scale = max|w|/127`
- 收益来源：权重读取量减半（1.11 GiB → 0.56 GiB），decode 带宽受限时理论上限 2×
- 代价：每层多一次 dequant（读 int8 + 写 fp16），可能抵消部分收益

| 指标 | 期望 | 判定 |
| --- | --- | --- |
| 权重显存 | -50% | 必达 |
| decode TPOT | +0~60% | 若为负，如实报告"带宽受限下不划算" |
| 精度 | logits 误差 | 报告 max/mean diff |

> 纯 PyTorch dequant-matmul **用不上 310B 的 INT8 张量核**；真 W8A8 需 ATC/AMCT 或 AscendC 量化 kernel，列为后续工作。

### 6.6 框架层算子融合

| 档位 | 内容 | 手段 | 实测/预期 |
| --- | --- | --- | --- |
| F1 | RMSNorm | `torch_npu.npu_rms_norm` | **5.09×**（已实测） |
| F2 | RoPE | `torch_npu.npu_rotary_mul` | 省去拼接与两次乘法 |
| F3 | Prefill 注意力 | `torch_npu.npu_fusion_attention` | 减少中间张量 |

### 6.7 AscendC 原生算子模块（本项目的技术纵深）

#### 6.7.1 为什么下沉到 kernel

框架层做不到的两件事：

1. **没有 paged 注意力算子**（CANN 8.1 的 211 个 310B 算子中不存在，torch_npu / MindSpore 也没有）。torch 版只能"gather 成 dense 再算"，多了一次全量 KV 拷贝和 padding 浪费。
2. **小算子密集**：每层要做 QK-Norm（2 次）、RoPE（若干次）等访存型算子，逐个调用会反复读写 GM。

#### 6.7.2 接口边界（下沉哪些算子）

| 算子 | 实现 | 理由 |
| --- | --- | --- |
| 线性层（q/k/v/o、MLP） | torch_npu matmul | 已有高效实现，无需自写 |
| RMSNorm | 框架算子 | 已实测 5× |
| **QK-Norm + RoPE 融合（K1）** | **AscendC** | 访存型，融合收益明确，难度中等 |
| **PagedAttention Decode（K2）** | **AscendC** | 消除 gather 拷贝与 padding，收益最大 |
| PagedAttention Prefill | 先 torch，后续可选 | prefill 可用 dense 路径，优先级低 |
| 采样 | torch / CPU | 延迟占比极小 |

#### 6.7.3 工程链路（板上组件已确认齐全）

```text
msopgen（算子工程生成，aarch64-linux/bin/msopgen）
   ↓ 生成 op_host/ 与 op_kernel/ 骨架
op_host/<op>.cpp       # tiling 函数：按 shape 计算切分参数
op_kernel/<op>.cpp     # __aicore__ kernel：GM ↔ UB 搬运 + 计算
   ↓ cmake（ascendc_kernel_cmake）→ bisheng 15.0.5 编译
custom_opp_<vendor>.run   # 自定义算子包，安装后进 opp/vendors/
   ↓
pybind11 小扩展 → 直接调 aclnn 接口（aclnnXxxGetWorkspaceSize + aclnnXxx）
   ↓
Python: nanoserve_ops.paged_attention_decode(q, k_cache, v_cache, block_tables, seq_lens, scale)
```

选择 **pybind11 + aclnn 直调** 而非 torch_npu 内部注册机制：接口边界清晰、不依赖未公开插件接口、可独立测试。

板上现有工具：`msopgen`、`ascendc_kernel_sample`、`tikicpulib`（CPU 仿真）、`msdebug`（kernel 调试）、`mssanitizer`（内存检查）、`mspti`（性能打点）、`cmake 3.22.1`、`g++ 11.4`；`pybind11` 需 `pip install`（清华源可用）。

#### 6.7.4 Kernel K1：QK-Norm + RoPE 融合

**输入/输出**（decode T=1；prefill T>1 走同一实现，按 T 分块）

```text
输入：q     [T, 16×128]  fp16   （q_proj 输出，未归一化）
      k     [T, 8×128]   fp16
      q_w   [128]        fp16   （q_norm.weight，逐头共享）
      k_w   [128]        fp16
      cos   [T, 128]  sin [T, 128]  fp16   （预计算 RoPE 表）
输出：q_out [T, 16, 128]  k_out [T, 8, 128]
```

**融合了什么**：per-head RMSNorm（q、k 各一次）+ rotate_half 拼接 + cos/sin 乘法。原本 6~8 次 kernel、多次 GM 往返，变为 1 次。

**tiling 设计**：

- 按 (token, head) 分核，每个 head 处理 128 维
- UB 单头需求：128 × 2B × 2（输入+输出）≈ 512 B，加归一化中间量仍很小
- 按 T 分块双缓冲：`T_tile` 取 64 或 128——**具体值需按 310B 实际 UB 容量标定**（M10 首个调试项）
- 归一化用 Vector 单元：`Mul → ReduceSum → Rsqrt → Mul`，与 DataCopy 流水重叠

**预期收益**：微基准 2~3×；端到端 TPOT 3~8%（该算子不是最大热点）。

#### 6.7.5 Kernel K2：PagedAttention Decode（核心）

**输入/输出**

```text
q           [B, 16, 128]                 fp16
k_cache     [num_blocks, block, 8, 128]  fp16
v_cache     [num_blocks, block, 8, 128]  fp16
block_tables[B, max_blocks]              int32
seq_lens    [B]                          int32
scale       标量
-> out      [B, 16, 128]                 fp16
```

**算法（flash-decode 风格 + online softmax）**

```text
for b in batch:
  for h in 0..15:                     # 16 个 q head，每 2 个共享 1 个 kv head
    kvh = h // 2
    m = -inf; l = 0; acc = zeros(128)
    for blk in block_tables[b]:
      DataCopy(k_blk <- k_cache[blk, :, kvh, :])    # block×128
      DataCopy(v_blk <- v_cache[blk, :, kvh, :])
      s = q[b,h,:] · k_blk^T * scale                # [block]
      s = where(valid_mask, s, -inf)                # 尾块无效槽位
      m_new = max(m, max(s))
      p = exp(s - m_new)
      l = l * exp(m - m_new) + sum(p)
      acc = acc * exp(m - m_new) + p · v_blk
      m = m_new
    out[b,h,:] = acc / l
```

**tiling 设计**：

- 按 (request, q_head) 分核，16 个 q head 可并行
- 每个 block 单 kv head 的 K/V 数据量：16 × 128 × 2B = 4 KB，双缓冲 8 KB，UB 压力很小
- **零拷贝关键**：kernel 直接按 `block_tables` 计算 GM 地址，`DataCopy` 从块池直读，**没有 gather 中间张量**
- 无需 padding：尾块用 `seq_len % block_size` 生成 valid mask

**预期收益**（设计假设，M10 验证）：

- kernel 级：相比 "index_select + bmm + softmax + bmm"，省掉全量 KV 拷贝与中间张量，预期 attention 耗时降低 **40~70%**
- 端到端：attention 在 decode 中占比约 20~40% ⇒ TPOT 降低 **10~25%**

#### 6.7.6 验证与调优方法

| 阶段 | 手段 | 通过标准 |
| --- | --- | --- |
| 单元正确性 | `tikicpulib` CPU 仿真，与 torch 参考实现逐元素比较 | 相对误差 < 1e-2（fp16） |
| 上板正确性 | 同一输入同时喂 kernel 与 torch 路径 | 同上 |
| 内存安全 | `mssanitizer` | 无越界/未初始化 |
| 性能 | `mspti` / `msprof` | 记录单 kernel 耗时并与 torch 版对比 |
| 端到端 | `KERNEL_MODE=torch|ascendc` 切换 | TPOT 降幅达标 |

#### 6.7.7 降级策略

- 每个 kernel 都有 torch 参考实现；`auto` 模式加载失败自动回退并告警。
- dynamic shape 需额外工作；首版按 shape 分档（T ∈ {1,2,4,8,16,...}）编译多份，边缘场景足够。

## 8. 性能模型与预估

### 8.1 Roofline

```text
Prefill:  T ≈ 2·P·S / FLOPS_peak / η_compute
Decode:   T ≈ (W + B·S·k) / BW_eff
其中 P=596M, W=1.11 GiB, k=112 KiB/token, B=batch, S=上下文长度
```

### 8.2 解码吞吐预测（待 M0 实测标定）

假设有效带宽 20~30 GB/s：

| batch | S=512 | S=2048 | 备注 |
| --- | --- | --- | --- |
| 1 | 15~22 tok/s | 12~17 tok/s | 权重读取主导 |
| 4 | 55~80 tok/s | 40~60 tok/s | KV 读取开始显著 |
| 8 | 90~130 tok/s | 55~85 tok/s | KV 占单步流量 30~50% |
| 16 | 110~150 tok/s | 50~75 tok/s | 接近计算拐点 |

**设计含义**：批处理是唯一能把 310B 从"能跑"变成"能用"的手段；KV 带宽随 S·B 线性增长 ⇒ **长上下文与高并发不可兼得**，这正是分页 + 前缀缓存的价值所在。

### 14.3 面试问答准备

1. **为什么不用 MindIE / ATB？** 二者都是昇腾面向数据中心的推理栈，硬件支持列表不含 310B；板上也确实不存在（无 `libatb*`、无 MindIE）。
2. **MindSpore 有 PagedAttention 为什么还自己写？** 有 Python 接口但没有 310B kernel（211 个算子中不含），实际调用会失败。
3. **为什么 torch 锁 2.1.0？** 板上 torch_npu 只有 2.1.0.post2 一个为 310B 编译的轮子；升级需重编且与 CANN 强耦合（8.5.0 在 310B 上会让初始化失败）。
4. **为什么不直接写 CUDA 风格 kernel？** 昇腾用 AscendC（bisheng clang + GM/UB 层次 + tiling），编程模型与 CUDA 差异大，需要重建内存层次直觉。
